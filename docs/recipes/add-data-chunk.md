# 配方：加一种数据块

工程包由若干定长块文件组成。加一种块 = 加一个文件约定 + 一个读写往返测试。

## 步骤

1. **写规范**（`docs/spec/gs3d-format.md`）：块名、块头字段、字节序（小端）、
   元素大小、对齐、版本。块头固定含 `magic`、`version`、`count`、`bytes`。
2. **块头常量**（`engine/data/<area>/`）：与规范同名同字段，`static_assert` 尺寸。
3. **写**（`engine/pipeline/writers/`）：只追加，不改已写块；写完再更新
   `manifest.json` 的块表（临时文件 + rename）。
4. **读**（`engine/data/<area>/`）：先校验块头与文件大小，再 `mmap`；不许先
   `reserve(count)` 后校验——伪造的 `count` 会直接吃掉内存。
5. **校**（`engine/data/format/Verifier`）：被 `verify` 命令和 ctest 共用。
6. **兼容**：旧程序遇到未知块类型必须忽略而不是报错（规则见 architecture.md
   不变量 5）。新程序遇到旧包缺块时给出明确提示。
7. **测试**：
   - 写→读回环，逐字段比对；
   - 截断文件（少一个块、块头声称的长度大于文件）必须被拒绝且不崩；
   - 未知块类型被忽略。

## 反面例子

复用已有记录结构体，靠"点在文件里多大"推断块布局。
仓库历史里 16 字节与 20 字节记录混用就是这类猜测造成的，靠另一层累加校验才没炸；
新格式不许再出现"布局隐含在长度里"。

## 检查

- [ ] 规范与代码字段一一对应
- [ ] 读取前先校验文件大小
- [ ] 截断与伪造长度都有测试
- [ ] manifest 最后写、原子替换
